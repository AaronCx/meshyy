# meshyy handoff — 2026-07-29

Written for whoever picks this up next. meshyy is in a rough state as an integrated
feature: the transport and daemon are sound and heavily tested, but the a+Terminal
integration has produced a run of user-visible bugs, several of which turned out to be
one cause wearing several disguises.

**Read this before touching anything, because three of the four bugs below were
misdiagnosed at least once, and two "fixes" made things worse.**

## Ground rules that do not bend

- **Clean-room.** Never clone, fetch, read or grep mosh's source, any fork, or any
  GPL/AGPL reimplementation. Design only from the USENIX ATC 2012 paper, man pages,
  RFCs, Apple docs, permissive code. Running mosh as a black box is allowed; reading how
  it works is not. If you think you need it: stop and ask.
- **`make check` before every push.** *(Corrected after 1b-zero: the second half
  of this rule is no longer true.)* CI now runs `swift test` unfiltered — the
  QUIC and client-session suites run on every merge, gated only by a bounded
  capability probe, and the CI log shows "MeshyyKit (real sockets, serialized)"
  passing on the runner. A green badge covers everything; `make check` before
  pushing remains the rule because it also runs the lint gates and catches
  failures before they burn a CI round-trip. The warning that used to sit here
  trained its reader to distrust the signal 1b-zero was spent earning — see
  docs/qa/known-debt.md for what replaced the gating.
- **§6.4 stream-equality is the invariant.** `StreamEqualityTests` and
  `CorpusOverTransportTests` are not negotiable and must never be weakened to make
  something else pass. Both caught real regressions this session.
- a+Terminal is **not** the project. It is the consumer. Aaron's standing instruction:
  "most issues most likely will stem from meshyy — I've already fleshed out this
  terminal app." That held up: every root cause below was meshyy's or the integration's,
  none was SwiftTerm's or the app's rendering.

## What was wrong, and what it actually was

### 1. The terminal would not resize (FIXED, merged, PR #18)

**Symptom, as reported:** "resizing does work but only after some time in a session,
never from the jump", later "not working at all now even after some time".

**Cause.** The kernel sends `SIGWINCH` on `TIOCSWINSZ` only when the size actually
CHANGES, and `PTYSession.resize` returned early when the requested size equalled the
recorded one. Together those made one state unrecoverable: a program out of sync with a
PTY **that is already the correct size**. The client sends the right number, the daemon
compares it to the number it holds, and neither the ioctl nor the signal happens — for
the life of the session.

**Evidence.** On Aaron's live session the PTY was `74x64` while tmux drew `74x39`, hours
later, with the phone re-sending `74x64` on every attach:

```
stty -f /dev/ttys090 size   ->  64 74
tmux list-clients           ->  74x39
```

**Fix.** `PTY.resyncSize` applies the size and signals the foreground process group
explicitly; the attach path uses it, the ordinary resize path is untouched.

**Trap that cost a green run:** `tcgetpgrp` on the pty **slave** fails with `ENOTTY` on
Darwin, silently, through a guard. Read it from the **master**. Same family as the
existing note in `PTY.init` about Darwin rejecting master-fd ioctls until the slave has
been opened.

**Why "making it more correct made it worse":** build 55 only ever fixed the size by
accident — the 10s app keepalive sent a *different* size, which counted as a change.
Build 56 sent the correct size immediately, which counted as no change at all.

### 2. "Reconnecting" every few seconds, flicker, and #1 (FIXED, merged, PR #20)

**This was one line, and it produced three separate-looking bug reports.**

`startHeartbeat` returned early when no `bootstrapProvider` was set — "nothing to
reconnect with". That conflates the loop's two jobs. Detecting a dead path needs a
provider. **Putting traffic on the connection does not**, and the probes are the only
traffic a quiet session produces. `MeshyyConnection.idleTimeoutMilliseconds` is **5000**.

a+Terminal drives its own reconnection, so it sets no provider, so it sent no probes,
so the transport was dropped five seconds after the user stopped typing. That surfaced
as:

- a "Reconnecting" flash every few seconds while sitting in a session
- flicker — every reconnect replays the screen
- **and bug #1's "only works after a while"**: the reattach path re-reads and sends the
  size, the first attach does not, so the size was only ever fixed by an accidental
  reconnect

Aaron's report that finally cracked it: *"when i first connect to the session it wont
resize, then after sometime i get a flash 'Reconnecting' and then i am able to resize."*

**The heartbeat now always runs.** Only the declare-dead branch is gated, and without a
provider it keeps probing rather than stopping — a session that gives up on its probes
guarantees the idle timeout it was trying to detect.

`QuietSessionSurvivalTests` asserts **survival** across a silence longer than the idle
timeout, deliberately not that probes were sent: counting probes passes on a client
sending them down an already-closed connection.

### 3. Flicker at session start (PARTLY FIXED, PRs #18 and #21)

Measured rather than guessed: a resume arrived as **two deliveries**, `146B` then `13B`
— the screen, then the geometry reset — and the second changes the scroll region, so the
emulator reflows a screen it has just drawn.

The replay now reaches the client as one `.output`, ended by the first non-PTY frame
(the daemon always sends `termios` next, from every version, so no protocol change and
no version skew).

**Two traps here, both already paid for:**

- An earlier attempt waited for an end-of-replay marker the daemon does **not** send
  when the replay is empty. It buffered live output forever on every fresh session.
  `SessionStartPaintTests.freshSessionIsNotHeldBack` pins that.
- Folding the geometry reset into the replay's `.output` to save the second delivery
  **breaks §6.4** — `outputBytes` is compared byte-for-byte against the PTY's stream
  across a reattach, and 13 locally generated bytes fail it. Do not do this. Merge the
  two deliveries in the *renderer* if it is still worth doing.
- PR #21 fixes a hole the coalescing introduced: a replay interrupted by a disconnect is
  already counted into `consumedOffset`, so it must be flushed before `.ended`/`.failed`
  or those bytes are lost silently. **`CorpusOverTransportTests` caught this on CI and it
  passes locally three runs for three** — that is how this class of bug reaches a user.

Note: the resync in #1 forces a redraw right after the replay by design, so there is a
small live repaint at session start. That is the cost of the terminal filling the screen.

### 4. New sessions land in old sessions (FIXED, merged, PRs #23 and #26 — both sides)

*(Status corrected after the fix landed; the lead below was right.)* The daemon
now owns allocation: `SessionStore.createLowestFree` with `reservedNames` and
`creating` makes the claim atomic, `GroupAllocationTests` covers it, and #26
stabilized the claim path. The a+Terminal half is ALSO done —
`lowestFreeMeshyySlot` no longer exists there (verified 2026-08-06: zero
references); the app asks the daemon for a new session and never computes a
slot locally, so the bug is fully fixed, not half.

Original entry, kept as written:

**Symptom:** "creating a new session is giving me a new session then randomly booting me
into different other meshyy sessions".

**Lead, and it looks conclusive from reading the code.**
`SessionManager.lowestFreeMeshyySlot(for:)` (a+Terminal, ~line 1119) computes the free
slot from **the app's currently open tabs**:

```swift
let taken = Set(sessions.filter { $0.server.id == server.id }.map(\.meshyySlot))
```

But meshyy sessions live on the **daemon** and outlive tabs — that is the entire point of
the feature. Close a tab, or get killed by iOS, and slot 0 is "free" locally while the
daemon still holds a live slot-0 shell. The next "new session" resolves to
`aplus-<server>-0` and drops the user into the previous shell.

The app's notion of free is local; the resource is remote. **The daemon is the source of
truth and should be asked** — `meshyyd list` is implemented and works
(`MeshyyTransport.daemonCommand("list")`). `MeshyySessionPileUpTests` already does
exactly this over a real connection and is the place to add the regression test.

Verify before fixing: reproduce by force-quitting the app with a session open, then
opening a new tab on the same server.

## Method notes, earned the hard way

- **Measure before fixing.** Every wrong turn this session was a fix aimed at a
  plausible cause. The kernel probes (`TIOCSWINSZ` reaching a tmux client;
  re-applying an unchanged size signalling nobody) each took under a minute and each
  settled a question that had absorbed hours of reasoning.
- **Plant the violation.** Every regression test here was confirmed red against the old
  behaviour. One that was not would have been worthless — the resync test passed against
  broken code until the `tcgetpgrp` bug was found.
- **A count on the far side beats any amount of client-side reasoning.** `meshyyd list`,
  `tmux list-clients`, `stty -f <tty> size`, `lsof <tty>` answered in seconds what four
  builds of guessing did not.
- **"It only breaks on meshyy, never on SSH" is a strong signal, not noise.** SSH closes
  the PTY on disconnect, so no stale program survives to drift and nothing is ever
  replayed. Both #1 and #3 live in exactly that gap — the cost of keeping the shell
  alive, which is meshyy's to pay.
